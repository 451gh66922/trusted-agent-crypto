# 课题技术边界与局限性分析清单 (供说明书与答辩使用)

本项目基于 RFC 9449 (DPoP) 与可插拔安全后端构建 AI Agent 可信授权体系。为体现客观严谨的工程思维，现将当前系统的实现边界、第三方组件局限性及软硬件差距详细梳理如下：

---

## 一、Keycloak (授权服务器 AS) 的 DPoP 校验边界

Keycloak 26.x 作为国际领先的开源身份基础设施，对 RFC 9449 提供了原生支持，但在实际 Agent 业务落地中存在以下边界：

1. 校验点仅覆盖 Token Endpoint (令牌端点)
   - 现状：Keycloak 只负责在 `/token` 换发和刷新阶段校验 DPoP Proof 的签名与 jkt 绑定。
   - 局限：Keycloak 本身不充当业务资源服务器 (RS)，无法为下游多变微服务自动提供业务请求时的 Proof 动态验签。
   - 我们的补全：架构中自研了轻量级 RS 中间件，补齐了业务访问阶段对 Authorization 与 DPoP 头的联合校验。

2. 默认不校验 ath (Access Token Hash) 声明
   - 现状：Keycloak 作为授权服务器，其签发的 Token 本身就是产物，因此在换发阶段 Proof 内无法包含未生成的 Token 哈希。
   - 局限：若资源服务器实现不严格，攻击者可能利用公钥签名合法的 Proof 去盗用另一个被泄露的 Token。
   - 我们的补全：在自研 RS 拦截器中，严格要求客户端在访问业务 API 时在 Proof 内注入 ath 声明，并在服务端强制进行 SHA-256 哈希比对，彻底闭环了“防挪用”。

3. 客户端凭据模式 (client_credentials) 默认行为
   - 局限：Keycloak 默认认为机器对机器 (M2M) 模式生命周期短，默认不签发 refresh_token。
   - 方案解决：必须在高级兼容模式中手动启用 Use Refresh Tokens For Client Credentials Grant，并在架构中固化为自动化导入配置 (realm-export.json)。

## 二、SoftSE (软件安全元件) 与真实硬件安全芯片 (Secure Element) 的差距

本项目主路径以 SoftSE 软件安全元件结合“插拔模拟”呈现，与物理硬件芯片相比存在客观差距与明确的移植点：

1. 侧信道攻击与物理探测防护
   - 真实硬件：具备防物理开盖探测、电压毛刺防御、能量分析 (DPA/SPA) 物理屏蔽能力。
   - SoftSE 局限：运行在操作系统进程空间，依赖内存隔离；若宿主机内核遭最高权限 Root 级内存 Dump，理论上存在内存扫描攻击面。
   - 说明书定性：SoftSE 实现了“无 export_private 接口”的软件硬约束与逻辑不出界，能够防御应用层与网络层的所有非特权攻击。

2. 授权根插拔的可控性差异
   - 真实硬件：插拔是基于 USB/I2C 总线中断的物理断电，授权根物理消失，具备绝对在场性。
   - 拔卡模拟：本项目通过 UnpluggedBackend 抛出 HARDWARE_NOT_PRESENT，在运行时彻底切断签名能力，逻辑等价于物理断线。
   - 移植点：统一抽象了 CryptoBackend 接口，未来只需接入基于 PKCS#11 的物理驱动即可直接无缝升级为真硬件，上层 DPoP 协议层无需改动一行代码。

## 三、策略门 (PolicyGate) 与审计留痕的局限

1. 策略上下文依赖客户端真实传递
   - 局限：策略门对 task_id、目标白名单的裁决，依赖客户端在签名时主动注入上下文字典。
   - 防御边界：若底层执行环境被完整篡改（例如修改了 client.py 源码跳过传参），需要依赖容器只读挂载或进程完整性校验。

2. 日志防篡改的本地局限 (W5 演进方向)
   - 现状：结构化日志追加写入本地 JSONL 文件。
   - 局限：若未引入远端只读日志收集服务或硬件 TPM 封印 (PCR 扩展)，本地日志仍存在被特权进程篡改的风险。
   - 规划：将在 W5 引入哈希链 (Hash Chain) 校验，确保事后日志被篡改可被数学证明与检测。

## 四、答辩总结一句话备忘

“我们清醒地认识到纯软件模拟在物理侧信道上的局限性，因此我们的核心创新聚焦于：在不改变现有工业基建 (Keycloak) 的前提下，通过统一安全后端抽象、密钥使用点策略硬门、以及严格闭环 RFC 9449 的 ath 双向绑定，在逻辑层彻底终结 Agent 凭据的泄露、挪用与越权滥用。”
